## Sharded Cluster (Шардированный кластер):

Это очень удобный (и экономичный!) способ горизонтального масштабирования БД.


### Схема шардированного кластера

```
                                    Клиенты
                                       │
                                       ▼
                                ┌─────────────┐
                                │   mongos    │  ← Query Router
                                └──────┬──────┘
                                       │
                 ┌─────────────────────┼─────────────────────┐
                 │                     │                     │
                 ▼                     ▼                     ▼
      ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
      │     Shard 1      │  │     Shard 2      │  │     Shard 3      │
      │   (≈ 1/3 данных) │  │   (≈ 1/3 данных) │  │   (≈ 1/3 данных) │
      │                  │  │                  │  │                  │
      │   ┌──────────┐   │  │   ┌──────────┐   │  │   ┌──────────┐   │
      │   │ Primary  │   │  │   │ Primary  │   │  │   │ Primary  │   │
      │   └────┬─────┘   │  │   └────┬─────┘   │  │   └────┬─────┘   │
      │        │         │  │        │         │  │        │         │
      │   ┌────▼─────┐   │  │   ┌────▼─────┐   │  │   ┌────▼─────┐   │
      │   │Secondary │   │  │   │Secondary │   │  │   │Secondary │   │
      │   └──────────┘   │  │   └──────────┘   │  │   └──────────┘   │
      │   ┌──────────┐   │  │   ┌──────────┐   │  │   ┌──────────┐   │
      │   │Secondary │   │  │   │Secondary │   │  │   │Secondary │   │
      │   └──────────┘   │  │   └──────────┘   │  │   └──────────┘   │
      └──────────────────┘  └──────────────────┘  └──────────────────┘
                 ▲                     ▲                     ▲
                 └─────────────────────┼─────────────────────┘
                                       │
                                ┌──────┴───────┐
                                │Config Servers│
                                │ (Replica Set)│
                                └──────────────┘
```

### Пояснения к схеме

- **Клиенты** всегда подключаются только к `mongos` (маршрутизатору запросов).
- **mongos** определяет, в каком шарде находятся нужные данные, и направляет запрос туда.
- **Config Servers** хранят метаданные кластера (какая часть данных в каком шарде). Обычно развёрнуты как Replica Set.
- **Каждый Shard** — это независимый Replica Set со своим Primary и Secondary.
- Все шарды вместе образуют одну логическую базу данных. 
- Данные распределяются между ними по shard key (условно по ≈ 1/3 в примере).

### Шардированный кластер (Sharded Cluster)

- **Статус:**  
  - Современный и активно используемый способ **горизонтального масштабирования** данных и нагрузки.

- **Назначение:**  
  - Позволяет распределять данные и нагрузку между несколькими серверами, когда одного Replica Set уже недостаточно.

- **Состав:**
  - **mongos** — маршрутизаторы запросов.
  - **Config Servers** — хранят метаданные (обычно Replica Set).
  - **Shards** — каждый шард является полноценным **Replica Set**. Это обеспечивает высокую доступность и отказоустойчивость внутри каждого шарда.

- **Репликация внутри кластера:**
  - Внутри каждого шарда репликация работает так же, как в обычном Replica Set (по умолчанию асинхронная).
  - Можно использовать `w: majority` — но только **внутри конкретного шарда**.
  - Миграция чанков (частей данных) между шардами происходит асинхронно.

- **Важное отличие от обычной репликации:**  
  - Шардирование решает задачу **масштабирования объёма данных и нагрузки**, а не только отказоустойчивости. 
  - Отказоустойчивость обеспечивается тем, что каждый шард — это Replica Set.


| Характеристика                        | Master-Slave              | Replica Set                     | Sharded Cluster                          |
|---------------------------------------|---------------------------|---------------------------------|------------------------------------------|
| **Основное назначение**               | Репликация                | Репликация + высокая доступность| Горизонтальное масштабирование данных    |
| **Автоматический выбор Primary**      | Нет                       | Да                              | Да (внутри каждого шарда)                |
| **Отказоустойчивость**                | Низкая (ручное переключение)| Высокая                        | Высокая (каждый шард — Replica Set)      |
| **Масштабирование**                   | Ограниченное              | Ограниченное (вертикальное + чтение)| Горизонтальное (данные и нагрузка)     |
| **Использование oplog**               | Да                        | Да                              | Да (внутри каждого шарда)                |
| **Возможность w: majority**           | Нет                       | Да                              | Да (только внутри шарда)                 |
| **Динамическая архитектура**          | Нет                       | Да                              | Да                                       |
| **Статус**                            | Устарел (с 4.0)           | Современный стандарт            | Современный стандарт                     |


### Как ведёт себя `mongos (Query Router)` при сложных запросах?

Если данные одной коллекции распределены по нескольким шардам, запрос (например, агрегация) обрабатывается следующим образом:

#### Как это работает

1. **Клиент** отправляет запрос (например, `aggregate`) в **mongos**.
2. **mongos** обращается к **Config Servers**, чтобы узнать, в каких шардах лежат нужные чанки данных.
3. Агрегация идёт **по всей коллекции**, следовательно, **mongos** понимает, что данные нужно взять из **всех** шардов.
4. **mongos** рассылает запрос **на все шарды** (это называется *scatter* — рассеивание).
5. Каждый шард выполняет свою часть агрегации **только над своими данными**.
6. Частичные результаты возвращаются обратно в **mongos**.
7. **mongos** объединяет (`merge`) результаты от всех шардов и отдаёт итоговый ответ клиенту.

```
Клиент
  │
  ▼
mongos  ──────►  Config Servers (узнаёт расположение данных)
  │
  ├────────────► Shard 1  ──► частичный результат
  ├────────────► Shard 2  ──► частичный результат
  └────────────► Shard 3  ──► частичный результат
  │
  ▼
mongos объединяет результаты
  │
  ▼
Клиент получает итоговый результат
```

### Важные моменты

- Этот процесс разделения запросов по шардам и объединения результат называется **scatter-gather** запросом.
- Агрегация по всей коллекции всегда будет обращаться ко **всем** шардам 
  - (если нет фильтра по `shard key`, который позволяет попасть только в один шард).
- Производительность таких запросов обычно ниже, чем на одном `Replica Set`, 
  - потому что появляется сетевой обмен и этап объединения результатов.
- MongoDB старается выполнять как можно больше стадий агрегации **на самих шардах**, 
  - а в mongos отправлять уже промежуточные результаты (чтобы уменьшить объём данных, которые нужно пересылать).
